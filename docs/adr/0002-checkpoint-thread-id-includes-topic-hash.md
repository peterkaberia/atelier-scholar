# LangGraph checkpoint thread_id includes a topic hash, not just session_id

`pipeline/orchestrator.py`'s `ResearchOrchestrator` runs the search pipeline as a LangGraph `StateGraph` checkpointed via `SqliteSaver`, keyed by a `thread_id`. The thread_id was originally just `session_id`: every pipeline run for a given session shared one checkpoint history, so an interrupted run (server restart, killed process, a Retry click) could resume from its last completed node instead of restarting.

That design assumed a session has exactly one search in its lifetime. It doesn't: `ui/callbacks/chat.py`'s `route_intent` can dispatch a *second* SEARCH-routed pipeline run against the same `session_id` when a follow-up needs genuinely new external results. Once a session's first search reached a completed checkpoint, `execute_full_search_pipeline`'s own early-return (`snapshot.values and not snapshot.next` → "already complete, skip re-run") fired unconditionally on every later call, silently returning the *first* search's stale `processed_records` — the new follow-up topic was never even looked at. Confirmed live: a follow-up like "write a 300-word abstract" that got misrouted to SEARCH produced a synthesis mixing the follow-up's own text as a mislabeled topic with the original search's citations.

**Decision**: `thread_id` is now `f"{session_id}:{sha1(topic)[:10]}"` — the same session_id namespace, but scoped further by a hash of the search topic itself.

**Consequences**: A genuinely different follow-up topic gets its own fresh checkpoint history and actually re-runs the pipeline, instead of being silently absorbed into an unrelated completed checkpoint. A true retry of the *same* topic (the common case - the original search failed and got retried) still hashes to the same thread_id and resumes correctly, since `ui/callbacks/chat.py`'s `retry_failed_search` rebuilds its retry query from the session's own stored topic. The one known gap: if a *follow-up*-triggered search (not the session's original one) fails partway through, `retry_failed_search` currently always retries using the session's original topic rather than the specific follow-up topic that actually failed - a pre-existing inconsistency this change didn't introduce and doesn't fully resolve, since it's a narrower edge case than the bug being fixed here.
